# Phase 2: daily check-ins and limited educational assessment

## Implemented workflow

Select a fictional astronaut in the existing shared selector, open Daily Check-In,
enter observations, submit, and inspect the saved result and previous entries.
The form displays mission context and supports precisely the existing CheckinCreate
fields: UTC check-in date/observation time, context, optional vital values, sleep,
mood/stress, exercise minutes, symptom entries and notes. At least one observation
is required. Missing values remain absent/null; zero is preserved as data.

Browser form validation matches structural shared bounds and canonical units. Blood
pressure requires both components. Backend Pydantic validation remains authoritative.
The server stores a DailyCheckin, linked manual HealthReadings, one Assessment and one
CommandReceipt in a single explicitly committed UnitOfWork. Failures roll back the
entire transaction. No health values are generated by GET requests.

The Phase 1 memory adapter already implements all required protocols and cross-record
constraints, so no new repository API or database implementation was necessary.

## API additions

All paths start with `/api/v1/astronauts/{id}`:

| Method | Suffix | Response |
|---|---|---|
| POST | /checkins | CheckinResult, HTTP 201; required UUID Idempotency-Key |
| GET | /checkins | Page[DailyCheckin], ascending observation time then ID |
| GET | /checkins/{checkin_id} | DailyCheckin, with reconstructed vital values |
| GET | /readings | Page[HealthReading], with documented reading filters |
| GET | /assessments | Page[Assessment], newest evaluation first |
| GET | /assessments/{assessment_id} | Assessment |

Collections retain limit/offset and from-inclusive/to-exclusive timestamps. Reading
filters retain indicator, source and simulation_run_id. Supplying simulator filters
does not start simulation; this endpoint can read unchanged representative fixtures.
Nested resources belonging to another astronaut return 404. Invalid fields/header
return 422, conflicts 409, storage failures 503, unexpected failures 500, using the
shared ErrorResponse. CORS now permits JSON POST and Idempotency-Key.

### Small API gap resolved without changing shared contracts

The Phase 0 API document specifies check-in list/create but has no individual
check-in GET route, although Phase 2 explicitly requests individual retrieval and
the repository provides get(id). The additive nested GET route above returns the
existing DailyCheckin DTO. This clarification was explained before implementation.
No shared DTO, enum, repository signature, fixture or file under shared/ changed.
No standalone assessment-generation POST or alert lifecycle is implemented here.

## Idempotency and transactions

The command hash contains the astronaut ID and normalized CheckinCreate payload,
including default fields, UTC timestamps and readings sorted by indicator. Receipt
operation includes astronaut ID. Same key/command returns the original stored result
with HTTP 201, including original IDs/timestamps; changed data or astronaut with the
same key returns idempotency_conflict (409). A different key for an existing daily
check-in returns conflict (409); check-in editing is outside scope.

Check-in and reading identities derive from the command/check-in UUIDs. Assessment
identity derives from check-in ID and ruleset version. Replays retrieve stored data
and verify reading completeness; they do not reevaluate or write records. Receipts
commit atomically with their result. ConcurrentWrite retries use up to three fresh
transactions, allowing concurrent identical commands to observe the winning receipt.
Other persistence failures propagate and roll back; no failed command receipt is saved.

The frontend retains an immutable payload/key pair for a retry. Editing the form
creates a new command on its next submission. Double-clicks are blocked synchronously
and inputs are disabled while saving. Astronaut changes unmount and abort the old
workspace, clear its form/results and ignore late responses. If an aborted request
already committed on the backend, it remains discoverable in that astronaut's history.
Network cancellation cannot undo a server commit. Drafts/command keys are not stored
across page reloads, but a previously committed entry is retrieved through history.
The page automatically opens the last-viewed check-in for the selected astronaut
after history loads. Only its ID is retained in tab storage, never health values.
If the backend no longer returns that ID, the latest available record or empty state
is displayed instead. Saved details appear above the form.

## Educational assessment limits

`checkin-demo-v1` is a small pure function separate from routers/repositories:

- Reported symptom entries produce review_suggested as an educational workflow flag.
  Their presence alone is the reason; no severity or diagnosis is inferred.
- Otherwise status is insufficient_data, even when all numeric fields were entered.
- Every result explicitly states that clinical evaluation and mission-specific
  clinical context are unavailable. No input is treated as reassuring medical evidence.
- Evidence includes supplied numeric observations and the reported symptom count,
  linked to persisted reading/check-in IDs. Text remains in the saved check-in.
- No physiological threshold, risk score, treatment, crew_medical_review escalation,
  background evaluation or alert generation is implemented. CheckinResult.alerts is [].

Prior seeded check-ins may have no linked assessment and are displayed that way.
The frontend associates new assessments through check-in evidence IDs, since the
shared Assessment DTO intentionally has no checkin_id field.

## Persistence and SQLite readiness

Entries survive frontend reloads while the same backend process remains alive.
Selected astronaut ID is retained in sessionStorage; invalid saved IDs fall back to
an available API profile. Selection still works when browser storage is unavailable.
Reload does not retain unsaved form drafts. Restart/reload of Uvicorn resets memory
to the fictional fixtures. In particular, --reload restarts after Python file edits.
The default reloader can watch Python tests too: saving a test file may reset the
running demo even though the browser was merely refreshed. For persistence checks,
use the startup command below without --reload and keep one backend process alive.
There is no durable storage, synchronization or database migration in this phase.

Services depend only on shared UnitOfWork/AdapterFactory protocols. Developer B
still owns SQLite/SQLAlchemy/Alembic, packaging, seeds and persistence tests. Future
integration must wire their factory into configuration, enforce command uniqueness
and atomicity, and run this workflow against SQLite. Selecting sqlite still fails
startup explicitly; no fallback or separate SQLite implementation was added.

## Run and test in PowerShell

From repository root, using your verified Python 3.13 `.venv`:

```powershell
.\.venv\Scripts\python.exe -m pip install -e './shared[test]' -e './backend[test]' -c backend/constraints-py313.txt
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Frontend, in a second terminal:

```powershell
cd C:\Users\WIN-X\astroguard-ai\frontend
npm.cmd ci
npm.cmd run dev
```

Dependencies did not change for Phase 2. Existing installations need only the startup
commands. A .venv313 environment with the same editable packages also works. Use
backend/.env.example and frontend/.env.example for optional environment overrides.

Tests from repository root:

```powershell
.\.venv\Scripts\python.exe -m pytest shared/tests backend/tests -q
.\.venv\Scripts\python.exe -m pip check
cd frontend
npm.cmd test
npm.cmd run build
```

## Manual acceptance procedure

1. Open http://127.0.0.1:5173/check-in; confirm API connected and a fictional crew profile.
2. Select Maya Demo. Keep today's UTC date (or a date without a seeded check-in).
3. Enter heart rate 72 bpm, blood pressure 120/80 mmHg, sleep 7.5 h, mood 4/5,
   stress 2/5 and exercise 30 min as fictional demo inputs.
4. Submit once. Verify confirmation, saved units, unknown omitted fields and an
   explicitly educational insufficient-information assessment.
5. Open the saved date in Previous check-ins and refresh the browser. Verify it
   remains listed and its details open above the form; the same selected astronaut
   is retained in this tab.
6. Switch to Leo Demo. Verify Maya's saved detail, success message and draft disappear.
7. Submit a notes-only entry on an unused date; no vital values should be invented.
8. On another unused date, report a fictional symptom and inspect the explained
   review-suggested flag. It must not claim a diagnosis or severity.
9. Try a partial blood pressure pair or SpO2 above 100; inline errors block submission.
10. Submit a second new entry for the same astronaut/date; the server returns 409.
11. Repeat an identical POST/key through API docs or an HTTP client; the result is
    identical with no new records. Change its payload with that key; expect 409.
12. Restart the backend and confirm process-local entries reset as documented.

Direct API inspection: http://127.0.0.1:8000/docs. The overview dashboard and advanced
history/alert pages are not extended by this phase; saved observations are viewed
inside Daily Check-In. No Phase 3 simulator or Phase 4 charts were added.
